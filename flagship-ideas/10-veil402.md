# Veil402 — Private Pay-Per-Use for Agent APIs

## Metadata

- **Target hackathons:** Monad (primary), Zcash (settlement), ETHGlobal
- **Tracks:** agentic commerce, payments, privacy, infrastructure, x402
- **Papers used:** Blockchain A2A payments SoK (2604.03733), MinMandate (2026/1674), Cloaked MCP (2026), AESP (2603.00318), Secure Agent Payments / TIVA (2511.15712), AP2 security analysis (2608.23858), Zcash linkability (1712.01210)
- **One-liner:** Pay-per-use APIs without telling the world which APIs your agent uses, which data it buys, or who it works for.

## The problem

x402-style payments make agent API calls payable with a blockchain transaction. That is great for machine-to-machine commerce and terrible for privacy:

- Every API call reveals the buyer, the seller, the endpoint, the time, and the price.
- A competitor can map an agent's workflow from its API payments.
- A merchant can price-discriminate based on an agent's history.
- A stable payment handle links calls across services, recreating the exact cross-merchant linkage that MinMandate identifies.
- On Zcash, shielding the payment helps, but exact amounts and timing at the boundary still leak. The 2017 linkability study linked 31.5% of entering coins with a simple amount/timing heuristic.

The A2A SoK's deeper finding is that payment finality is not service completion. A private payment that does not bind delivery is still a bad commerce primitive.

## The solution

Veil402 is a **private pay-per-use layer** for agent APIs.

1. **Per-call payment views.** The agent derives a fresh payment view for each API call, with no stable cross-merchant handle. The merchant sees a one-time authorization, not the agent's identity or history.
2. **Task-scoped API mandate.** The human approves a task budget and service classes ("market data, translation, enrichment"), not a list of endpoints. The agent can choose providers at runtime.
3. **Sealed provider selection.** For price-sensitive APIs, the agent runs a small sealed-bid request for quotes. Providers submit encrypted prices; the agent picks the best. Losing providers do not learn the winning price or the buyer's budget.
4. **Batch settlement.** Calls are batched into a single settlement window. The chain sees a batched shielded transfer, not one transaction per API call. This reduces timing and amount correlation.
5. **Receipt binding.** Each call returns a signed receipt binding the request hash, the response hash, the price, and the payment. The merchant cannot claim payment without delivery; the agent cannot claim delivery without payment. This closes the A2A payment-service decoupling gap.
6. **Private API credentials.** The agent proves it is an authorized buyer with a BBS+ credential; the API verifies the predicate without learning the human or the agent's other subscriptions. Revocation is handled by a status credential.
7. **Monad execution.** The API gateway, quote commitments, receipts, and nullifiers live on Monad for high throughput and low fees. The payment can be a Monad stablecoin or a Zcash-shielded note bridged into the settlement layer.
8. **Privacy budget.** The agent tracks how much it reveals across calls (provider set, timing, amounts) and warns when a sequence is likely to be linkable. The Zcash linkability lens is the model.

## Why this is out of this world

x402 is a payment rail. Veil402 is a **private market for API calls**: the agent can shop across providers, hide its workflow, batch settlement, and bind delivery, all without a stable identity. It turns the API economy from a surveillance feed into a private procurement market.

The demo: an agent buys market data, translation, and enrichment from three providers. A chain analyst sees one batched shielded settlement and three receipts, but cannot reconstruct the workflow. A malicious provider tries to charge without delivering; the receipt binding rejects the payment.

## Intuitive workflow

1. **The human approves an API budget.** "Up to 2 ZEC for market data, translation, and enrichment this week."
2. **The agent discovers providers.** It requests quotes. Providers submit sealed prices.
3. **The agent picks the best combination.** It does not reveal its budget or the losing quotes.
4. **The agent calls the APIs.** Each call uses a fresh payment view and a BBS+ authorization proof.
5. **The API returns data and a receipt.** The receipt binds the request, response, price, and payment.
6. **The agent batches settlement.** One shielded transfer covers the window; the chain does not see one transaction per call.
7. **A provider fails to deliver.** The receipt binding blocks payment or triggers a refund.
8. **A competitor scrapes the chain.** It sees a batched settlement and receipts, not the agent's workflow.

## Demo (5 minutes)

**Act 1 — The leak.** Show x402 calls: the chain reveals the agent's API graph, prices, and timing. A competitor reconstructs the strategy.

**Act 2 — The private call.** The agent uses a fresh payment view and a BBS+ credential. The provider verifies authorization; the public sees no stable handle.

**Act 3 — The sealed quotes.** Three providers submit encrypted prices. The agent picks the best. The losers do not learn the winning price.

**Act 4 — The receipt.** A provider tries to take payment without delivering. The receipt check fails.

**Act 5 — The batch.** Ten API calls settle in one shielded batch. The linkability lens shows the timing/amount correlation drop.

**Close:** "Your agent's API bill is not its business model."

## Cons and risks

- **Batching latency.** Settlement windows delay provider payment; some APIs need instant settlement.
- **Provider adoption.** APIs must verify BBS+ credentials and return signed receipts.
- **Privacy vs chargeback.** A fully private payment makes disputes harder; the receipt and bond design must handle fraud.
- **Cross-chain complexity.** Monad + Zcash bridge is a trust surface; a hackathon demo can mock it.
- **Traffic analysis.** Batching reduces but does not eliminate timing correlation; network metadata remains.
- **Credential issuance.** Who issues the API-buyer credential? A centralized issuer is a trust anchor.
- **Price privacy.** Sealed quotes require a committee or TEE; a malicious coordinator can leak.
- **No audit.** The protocol is a prototype.

## Judge Q&A

**"How is this different from x402?"** x402 settles a payment; Veil402 hides the workflow, enables provider competition, batches settlement, and binds delivery. It is a private commerce layer, not just a payment rail.

**"Why not just use Zcash directly?"** Zcash hides the payment, not the API authorization, quote selection, or receipt binding. Veil402 adds the market semantics.

**"How do you prevent double spending?"** A one-time nullifier per call, bound to the payment view and the receipt.

**"What if the provider cheats?"** The receipt binds request, response, and payment; a dispute/bond path handles failure. It is not trustless.

**"Why Monad?"** Cheap, high-throughput per-call checks and receipts; batching is practical.
