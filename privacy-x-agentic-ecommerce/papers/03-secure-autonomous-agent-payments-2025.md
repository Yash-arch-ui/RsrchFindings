# Secure Autonomous Agent Payments: Verifying Authenticity and Intent in a Trustless Environment

- Venue/ID: arXiv:2511.15712v1 [cs.CR]; preprint (the PDF uses a generic "Journal of LaTeX Class Files" template, not an actual journal venue)

## One-paragraph summary
The paper proposes TIVA (Trustless Intent Verification for Autonomous Agents), a blockchain-based framework that tries to establish both who an AI agent is and why it is paying. TIVA combines four components: decentralized identifiers (DIDs) and W3C verifiable credentials for agent identity and delegation; on-chain intent proofs in the form of either pre-signed mandates or a dynamic policy contract; zero-knowledge proofs for selective disclosure and policy-compliance proofs; and optional trusted execution environment (TEE) attestations for the agent's code and keys. The design centers on an Agent Wallet Contract that holds or controls funds and only releases them when the agent's signature and a valid intent proof are presented. The paper's evaluation is qualitative: it argues that the design resists impersonation, unauthorized payments, and intent misalignment, and discusses fraud reduction, regulatory alignment, and interoperability. Its contribution is an architectural synthesis, not a validated system.

## Problem and threat model
Autonomous agent payments break the traditional assumption that a human is present at checkout to provide authentication and intent. The paper separates two questions. Authenticity asks whether a transaction genuinely originates from a legitimate, authorized agent acting for a particular principal, rather than an impersonator or unauthorized code. Intent asks whether the transaction's purpose and details align with what the user actually permitted.

The threat model is described informally rather than formalized. The relevant adversaries include an impersonator who lacks the agent's private key, a compromised agent or stolen agent key, a malicious payee or merchant, a user who later repudiates a payment, and an attacker who steals both the agent and user keys. The framework also assumes an adversary may exploit weak mandates, replay a valid authorization, or submit a payment outside the encoded constraints.

Trust assumptions are important and somewhat tension-laden. The paper repeatedly calls the system "fully trustless" and says no centralized authority or intermediary is needed, but it relies on a DID registry, verifiable credential issuance and revocation, smart contract correctness, blockchain consensus, and, optionally, a TEE hardware manufacturer. The TEE path explicitly involves trusting the hardware vendor. The paper does not provide a formal adversary capability model, nor does it analyze collusion, MEV, transaction graph leakage, or denial of service in depth.

## Architecture / protocol / taxonomy
TIVA splits into an off-chain agent domain and an on-chain verification domain. The off-chain domain hosts the AI worker agent, optionally inside a TEE, for decision logic and key storage. The on-chain domain contains the DID/credential registry and the Agent Wallet Contract that enforces payments. Figure 1's flow is: (1) the user wallet issues verifiable credentials; (2) the wallet verifies DID/credential; (3) the agent submits a payment request; optional policy and zero-knowledge modules support rule evaluation and privacy.

Identity and delegation. Each agent gets a DID and cryptographic credentials. The user or organization issues a delegation credential as a W3C Verifiable Credential attesting the agent's identity and permitted actions. The paper's example is: "Agent X is authorized to spend up to 5 ETH per day from account Y for the purpose of cloud services." The credential is signed by the user's private key and can include spending limits, permitted payees or categories, and expiration. Credentials are stored off-chain for efficiency, with a digest or ID anchored on-chain in a DID registry or credential registry for discovery and revocation checks. Verification checks the issuer's signature against the issuer's public key in the DID registry and confirms the credential has not been revoked.

Intent proofs. TIVA supports two modes. Pre-signed mandates are user-signed structured authorizations for a specific task or transaction, for example "Agent X may buy up to 3 units of item Z at $100 each from vendor Y before DD/MM/YYYY." The agent attaches the signed mandate when paying. The Agent Wallet Contract verifies the user's signature and checks that the transaction details do not exceed the mandate's item, quantity, price, vendor, and expiry constraints. Dynamic on-chain policy is the second mode: the user deploys a policy contract encoding rules such as "Agent X can spend up to 10 USDC per day on cloud services; anything beyond requires my manual approval." The contract checks current state, such as how much the agent has spent today, and authorizes or blocks the transfer. The agent's DID ensures only the legitimate agent can invoke the contract on the user's behalf.

The Agent Wallet Contract combines these roles. It is a smart contract wallet that holds the agent's spending funds or controls access to the user's funds, and it enforces mandate or policy checks on every transaction. Only the agent's DID public key is authorized to initiate payments, and each call must include a valid intent proof. The contract verifies the agent signature and the intent proof before executing the transfer. Every authorized payment produces an on-chain event log linking the transaction to the intent proof. Stolen credentials or malicious code alone cannot transfer funds without the proper user-signed intent.

Zero-knowledge proofs. TIVA uses ZKPs in two ways. Selective disclosure of credentials lets the agent prove it possesses a credential with attributes meeting requirements without revealing the whole credential. The example is a credential allowing up to $500; instead of revealing it, the agent proves "I have a credential issued by User U that authorizes at least $500 of spending," hiding the actual limit and other permissions. Intent compliance proofs let the agent prove that the transaction complies with the user's approved parameters without revealing those parameters. For example, if the mandate says purchase item Z only if price is at most $100, the agent proves "I have a signed mandate from the user and the price in this transaction does not exceed the mandate's price limit." The contract verifies the proof using an on-chain zk-SNARK verifier or an off-chain verification followed by an on-chain validity check, against the user's public key. If the agent tries to exceed the limit, it cannot produce a valid proof and the contract rejects the transaction.

Secure execution. TEEs such as Intel SGX or ARM TrustZone run the agent code in an isolated enclave. The agent can produce a remote attestation, a cryptographic quote proving the code is genuine and untampered. TIVA can verify the attestation on-chain via a known attestation contract or oracle before accepting the agent's actions. In practice, the Agent Wallet Contract would require an attestation quote or use a set of whitelisted enclave public keys with transactions. Only if the quote is valid, meaning the code hash matches approved code and is running in real hardware, will the contract honor the request. If TEEs are unavailable, the paper recommends at least an HSM or software vault for keys.

## Section-by-section findings
- Section I frames the authenticity and intent gap, reviews A2A/AP2, DIDs/VCs, Shade on NEAR, and Coral Protocol session vaults, and states that no unified framework combines identity, intent verification, proofs, and secure execution.
- Section II is the methodology and architecture. It defines DID/VC delegation, the two intent-proof modes, the Agent Wallet Contract, ZK selective disclosure and compliance proofs, and optional TEE attestation.
- Section III is a qualitative analysis of five properties: impersonation resistance, intent verification, trustless decentralization, auditability, and privacy. It also discusses credential forgery, key compromise, and revocation.
- Section IV discusses user empowerment, fraud reduction and merchant confidence, regulatory alignment (KYC/AML, consumer consent), and interoperability with A2A and AP2.
- Section V concludes and lists future work: a prototype on a live blockchain, smart contracts for credential and proof verification, performance and gas assessment, richer intent representations, domain-specific policy languages, and multi-agent joint intent proofs.

## Key mechanisms and equations
No equations are given. The key mechanisms are the credential schema (spending limits, permitted payees or categories, expiration), the two intent-proof forms, and the verification predicates in the Agent Wallet Contract. The paper gives no contract or function names, no circuit specification, no commitment scheme, no nullifier design, and no serialization format. The closest thing to a formal statement is the ZK proof claim: prove possession of a user-signed mandate and prove that the transaction amount is at most the mandate's limit, without revealing the price or limit.

The paper mentions zk-SNARKs and says proofs can be verified with "minimal gas cost" but provides no measurement or curve/backend choice. It also mentions threshold signatures from enclaves but does not specify a threshold scheme.

## Experiments / evaluation
There are no experiments. The evaluation is a qualitative security analysis, not a measurement study. There are no datasets, baselines, metrics, gas costs, latency numbers, throughput numbers, false-positive rates, or prototype results. The paper itself says future work will implement a TIVA prototype in a live blockchain environment to assess performance, gas costs, and user experience. Claims such as "minimal gas cost" are assertions, not findings; the only evidence is architectural reasoning and references to other systems.

## Paper-specific findings
1. TIVA's core novelty is the combination of DID/VC identity, on-chain intent proofs, ZK compliance, and optional TEE attestation in one architecture, not the invention of any single primitive.
2. The dual-key requirement is the main impersonation defense: the agent's key proves the agent, the user's signed credential proves authority, and one stolen key is insufficient.
3. Intent is reduced to enforceable, quantifiable constraints (item, quantity, price, vendor, expiry, daily spend), not to semantic alignment with the user's deeper goals.
4. The Agent Wallet Contract is both custodian and policy enforcement point; the paper explicitly wants all validation logic on-chain to avoid a centralized approver.
5. ZK proofs are used for both credential selective disclosure and transaction-level compliance, which is a useful separation of identity privacy from policy privacy.
6. The design supports revocation by marking a credential revoked on-chain, which stops future transactions once compromise is detected.
7. TEE attestation is optional and explicitly shifts trust to the hardware manufacturer, which sits awkwardly with the "fully trustless" framing.
8. No implementation, circuit, contract, or benchmark is provided; the security analysis is argumentative.

## Limitations and caveats
The paper's own limitations are implicit rather than a dedicated section: it has no prototype, no performance or gas evaluation, no formal security proof, no concrete ZK circuit, no smart contract specification, and no user study. It also does not address key rotation, replay/nullifiers, MEV, chain reorgs, credential revocation privacy, or the governance of the DID registry.

Additional caveats: "fully trustless" is overstated because the design depends on DID registry governance, credential issuers, smart contract correctness, blockchain consensus, and optionally a hardware vendor. The ZK claims are high-level; without a circuit and trusted-setup/transparency discussion, the privacy and soundness properties are unproven. Selective disclosure can still leak metadata through timing, amounts, and transaction graph. The claim that an agent "cannot initiate a payment that the user did not intend" is only true for the quantifiable constraints encoded in the mandate or policy; an agent can still act within scope in undesirable ways, which the paper acknowledges. The AP2 and A2A citations are descriptive, not interoperability. There is no discussion of dispute arbitration or delivery proof.

## Hackathon hooks
What it enables: a clear architectural pattern for combining verifiable delegation with an on-chain policy wallet. The mandate structure and the two ZK statements are good demo starting points. The Agent Wallet Contract is a natural Monad demo because cheap execution makes per-transaction policy checks practical.

What it does not enable: it does not provide production ZK circuits, a concrete AP2 integration, on-chain privacy for the transaction graph, or a trustless TEE. It does not guarantee semantic intent alignment, prevent a compromised agent from acting within its allowed scope, or protect against a compromised user key. It does not specify replay protection or nullifiers, so a naive implementation would be vulnerable to mandate reuse.

Demo ideas: (1) an Agent Wallet Contract on Monad that verifies a user-signed mandate and rejects over-limit or expired purchases; (2) a zk-SNARK proof of "amount <= limit" with the limit hidden, using a simple circuit and an on-chain verifier; (3) a DID/VC issuance and revocation flow with selective disclosure of a spending tier; (4) a side-by-side demo showing that a stolen agent key alone cannot spend without the user credential.

## Claims to avoid
Do not claim TIVA is fully trustless, implemented, benchmarked, or formally verified. Do not claim it guarantees user intent beyond encoded constraints. Do not claim "minimal gas" or any performance figure; none were measured. Do not claim the ZK proofs are deployed or that the circuit is specified. Do not claim TEE attestation is trustless; it trusts the hardware manufacturer. Do not claim it provides full transaction privacy; it hides selected credential and mandate fields, not the transaction graph. Do not claim it eliminates fraud or chargebacks; those are argued benefits, not results.
